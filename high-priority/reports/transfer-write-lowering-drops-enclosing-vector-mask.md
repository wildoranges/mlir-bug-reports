# [fuzzer-found][mlir][VectorToArmSME] transfer_write lowering drops enclosing vector.mask (invalid IR)

`vector.mask` requires a `MaskableOpInterface` payload in its region, and after the verifier tightening in #240797 a masked `vector.transfer_write` takes its mask from the enclosing `vector.mask` region rather than from an operand on the payload. `TransferWriteToArmSMELowering` builds the replacement from `writeOp.getMask()` only, so when the greedy driver matches a `vector.transfer_write` nested inside a `vector.mask`, that operand is null and the replacement has no mask. The conversion patterns live in VectorToArmSME.cpp:

https://github.com/llvm/llvm-project/blob/8445b527ed0da1f9156f27be8c193624d0292253/mlir/lib/Conversion/VectorToArmSME/VectorToArmSME.cpp#L121-L156

On the reproducer, the pass rewrites the in-bounds, identity-map payload to an unmasked `arm_sme.tile_store` with `operandSegmentSizes = array<i32: 1, 1, 2, 0>` and leaves it inside the `vector.mask` region. The resulting IR no longer satisfies `MaskOp::verify`, which reports `error: 'vector.mask' op expects a MaskableOpInterface within the mask region`, both as a diagnostic and on re-verification of the printed output. The mask operand `%mask` has been dropped instead of being preserved or applied to the tile store.

`repro.mlir`:
```mlir
func.func @masked_write(%base: memref<?x?xf32>, %v: vector<[4]x[4]xf32>, %mask: vector<[4]x[4]xi1>, %c0: index) {
  vector.mask %mask { vector.transfer_write %v, %base[%c0, %c0] {in_bounds = [true, true]} : vector<[4]x[4]xf32>, memref<?x?xf32> } : vector<[4]x[4]xi1>
  return
}
```
